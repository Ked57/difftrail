# Graph extraction across deleted and renamed modules

Research date: 2026-10-15. Resolution evidence for [Establish graph-extraction limits for deleted and renamed modules](https://github.com/Ked57/difftrail/issues/4), within [Map: specify Difftrail as a reusable impacted-file CLI](https://github.com/Ked57/difftrail/issues/1).

## Scope and method

The agreed destination is an implementation-ready specification for a reusable TypeScript/JavaScript tool that emits impacted files for the latest commit or an optional range. Consumers, including people and LLMs, connect that output to their chosen tools. Runner integration and the safety response to uncertainty remain product decisions.

This is documentation and source-code research, not a runtime experiment. Dependency-cruiser is a candidate, not a selected dependency. Its official source was inspected at commit `c580daf6477aa5619bacad9c9091c9b7cc81882d`; that snapshot declares version `18.6.0`. Links below pin that snapshot so later changes do not silently change the evidence. [Package metadata](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/package.json)

The earlier local note, `~/Documents/Codex/2026-10-14/che/outputs/incremental-testing-clis.md`, compared changed-file tools, graph tools, and runner-native selectors. The relevant reusable context is retained here: a Git change list is an input, not a dependency closure; dependency-cruiser supplies module-level graph output and reverse reachability, making it a candidate for file-level selection. Its `--affected` convenience option is documented as `--reaches` seeded by changed paths, with `main` as its default revision. That default is historical tool behavior, not Difftrail's latest-commit requirement. This research does not repeat the runner shortlist. [CLI reference](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/doc/cli.md#--affected-show-modules-and-their-transitive-dependents-since-a-git-revision)

The CLI's `--affected` normalization calls watskeburt with an old revision and output type `regex`, then sets `reaches`. ## Base/head consequences — inference from verified mechanics

The following are deductions, not claimed executions of dependency-cruiser fixtures. They follow from filesystem extraction, unresolved resolution behavior, and reverse traversal linked above. For this discussion an edge `A → B` means A imports B.

| Change | Evidence in a base snapshot | Evidence in a head snapshot | Consequence |
| --- | --- | --- | --- |
| Delete B and remove its imports | B and incoming `A → B` edges can exist. | B and those edges are absent. A is itself changed if its source import was removed. | Head cannot reproduce B's former incoming edges. This does not prove every deletion causes a missed file: seeding changed importers can cover their current dependents. |
| Delete B but leave `A → B` in source | Previously resolved B and canonical incoming edges. | An unresolved dependency may remain, keyed by the original specifier such as `./b`, rather than former canonical `src/b.ts`. | Matching a changed canonical filename against unresolved head nodes is not guaranteed to find A. |
| Rename B to C and update importers | Old path and old incoming edges. | New path and new incoming edges; edited importers are changed seeds. | Neither graph alone supplies rename identity. Git's old/new path pair is separate evidence. |
| Remove `A → B` while retaining B | Old edge. | Edge absent; A is a changed seed. | Traversing only from B on head loses that former edge; traversing from changed A may already include its consumers. Historical edges and required output are separate questions. |
| Retarget an import through alias/config changes | Resolution under old config/environment. | Resolution under new config/environment. | Unedited source files may change their resolved targets; changed source paths alone need not describe those changed graph edges. |

The unresolved-name behavior is source-verified: the CommonJS/ES resolver initializes `resolved` to the stripped source specifier, attempts resolution, and sets `couldNotResolve: true` on failure. It catches resolution errors without preserving the underlying exception in that dependency object. Extraction can add such non-followable dependencies as graph nodes with empty dependency lists. [Resolver](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/resolve/resolve-cjs.mjs), [Extraction/completion](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/index.mjs)

Git can provide statuses and rename pairs using name/status or raw output with rename detection; `-z` avoids quoting ambiguities in unusual filenames. Rename detection uses similarity criteria, so rename identity is detected metadata, not a universal identity guarantee. `git diff A B` compares endpoints, while three dots use a merge base. These are factual distinctions for the revision-contract decision, not a recommendation to select either interpretation. [Git diff manual](https://git-scm.com/docs/git-diff)

**Implication, not selected architecture:** retaining or extracting both endpoint graphs makes disappeared edges available for later policy decisions. A possible analysis is separate reverse closures in each snapshot, reconciled through a Git path/status map. Blindly combining edges from both snapshots can create paths that existed in neither snapshot; whether that extra selection is acceptable is a policy decision. These are mathematical consequences of two graphs, not dependency-cruiser features. Historical extraction also needs the relevant historical configs and a compatible resolver/dependency environment; checking out old source while resolving against unrelated current packages is not evidence of the old graph.

## Uncertainty is observable only in part

- **Observable unresolved edges:** `couldNotResolve` identifies imports that extraction recognized but resolution could not locate. `followable: false` alone is not an error: built-ins and deliberately unfollowed dependencies also have this value. [Result attributes](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/types/cruise-result.d.mts)
- **Unobserved variable imports:** official documentation supports literal-string dynamic imports and templates without placeholders, and explicitly excludes variable/expression imports and requires. The JavaScript extractor only pushes recognized literal/template imports; its other branch adds no unknown-edge record. Therefore a graph with no unresolved edges is not a completeness certificate. This last conclusion is an inference from those mechanics. [FAQ](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/doc/faq.md#q-does-dependency-cruiser-handle-variable-or-expression-requires-and-imports), [Import extractor](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/acorn/extract-es6-deps.mjs), [Require extractor](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/acorn/extract-cjs-deps.mjs)
- **Tolerant parsing:** the Acorn path falls back from its strict parser to `acorn-loose` on parse failure; this catch does not emit a structured warning. Consequently successful extraction cannot by itself certify syntactically valid source. This is source inspection of that parser path, not a statement about all parsers or transpilers. [Parser](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/acorn/parse.mjs)
- **Scope omissions:** extraction follows recognized dependencies subject to followability, `doNotFollow`, maximum depth, and dynamic exclusions. Output filters can further remove nodes and edges. The absence of a file can therefore mean it was excluded rather than unaffected. [Extraction](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/index.mjs), [Filters](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/graph-utl/filter-bank.mjs)

No reviewed contract establishes a universal uncertainty/completeness field covering all omitted imports, dynamic loading, configuration effects, or non-code inputs. That is a bounded research finding, not proof that no related feature exists anywhere. Which conditions make Difftrail fail, warn, or expand its output remains open.

## TypeScript aliases and workspace boundaries

1. `tsConfig` supports an explicit config and its `extends` hierarchy, but the documented cruise behavior uses `compilerOptions`, not `files`, `include`, or `exclude`. Raw programmatic transpile options do not automatically flatten `extends`; the provided `extract-ts-config` utility does. That utility can silently return an empty object when a supported TypeScript compiler is unavailable and throws on unreadable/invalid configs when it is available. [TS configuration documentation](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/doc/options-reference.md#tsconfig-use-a-typescript-configuration-file-project), [API types](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/types/dependency-cruiser.d.mts), [Extraction utility](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/config-utl/extract-ts-config.mjs)
2. Resolver normalization installs `TsConfigPathsPlugin` for the configured config. Its inspected interface selects one config filename; this is not evidence of automatically choosing every package's tsconfig or following TypeScript project references. It uses enhanced-resolve; default `exportsFields` is empty for compatibility, so package exports/conditions may need explicit matching configuration. [Resolver normalization](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/main/resolve-options/normalize.mjs)
3. TypeScript's `paths` tells the compiler how to resolve imports and does not rewrite emitted import specifiers. Therefore successful alias resolution for analysis does not establish agreement with the user's runtime or bundler. [TypeScript paths reference](https://www.typescriptlang.org/tsconfig/paths.html)
4. By default type-only/pre-compilation dependencies are omitted; `tsPreCompilationDeps: true` includes them, and `"specify"` additionally identifies dependencies existing only before compilation. This changes the graph a reusable selector would consume and remains a product decision. [Pre-compilation option](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/doc/options-reference.md#tsprecompilationdeps), [Extraction selection](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/extract-dependencies.mjs)
5. Monorepo dependency classification normally uses the closest package manifest; `combinedDependencies` can merge manifests toward the cruise root. Symlinks resolve to real paths by default. Workspace alias classification exists, including explicitly described best-effort handling when symlinks are preserved. Classification support is not proof that uninstalled workspace packages or missing built entrypoints resolve to source. [Monorepo and symlink options](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/doc/options-reference.md#preservesymlinks), [Workspace classification source](https://github.com/sverweij/dependency-cruiser/blob/c580daf6477aa5619bacad9c9091c9b7cc81882d/src/extract/resolve/module-classifiers.mjs)

## Remaining validation and decisions

Before a specification claims supported behavior, a future fixture should exercise: deletion with and without importer edits; rename with and without detection; removed imports and barrel re-exports; config-only alias retargeting; literal versus variable dynamic imports; type-only imports; multiple package tsconfigs/project references; workspace source versus missing built entrypoints; exports conditions; and realpath versus preserved-symlink identity. The fixture should capture full graphs and diagnostics at both endpoints before asserting selected output. This is proposed validation work, not work performed here.

Research resolves what the candidate exposes and why head-only reachability cannot recover all historical relationships. It does not choose graph backend, graph snapshot strategy, output treatment of deleted paths, acceptable over-selection, supported workspace layouts, or any fallback/safety policy. No candidate dependency was installed and no runnable Difftrail behavior changed. The documentation artifact was checked for whitespace and local source-link targets; no runtime/manual QA surface applies.
